## 五轴代码审查（code-review-and-quality skill）

审查对象：HEAD 上 AI 记账链路 + 交易写入路径（工作区无代码改动）。

**两个 Critical（均为静默账目损坏，359 个 Rust 测试抓不到）：**

1. **快速记账与 AI 记账无事务**。`commands/transactions.rs:359 quick_add_transaction` 与 `commands/ai.rs:214 ai_parse_transaction` 直接调 `db::transactions::quick_add_transaction(&conn, ...)`，未开事务；而 `transaction_create`（:265）开了事务并 commit。db 层 `create_transaction` 在 autocommit 下 INSERT transactions 后循环 INSERT postings，中途失败会留下不平衡的孤儿交易。更糟的是 `ensure_category_account`（`db/transactions.rs:430`）和 `resolve_category`（`commands/ai.rs:16`）还会各自 INSERT accounts / categories，AI 路径一次调用最多 4+ 次独立写，全无原子性。`db/transactions.rs` 里 ~20 个 quick_add 测试全部直传 `&Connection`，无一条测失败路径。
   - Remedy：把事务下沉到 `db::transactions::quick_add_transaction` 内部（用 `conn.unchecked_transaction()` 保持 `&Connection` 签名），别在 IPC 层各加一遍。
2. **金额解析 f64 饱和**。`db/transactions.rs:331 parse_amount_to_cents` = `(value * 100.0).round() as i64`，项目"金额用整数分、从不用浮点"规则在 AI 路径被绕过。`services/ai.rs:51 validate_amount` 只判 `v > 0.0`，`inf` / `1e309` 会通过；实测 `"1e309".parse::<f64>() * 100.0 as i64 == 9223372036854775807`（已用 rustc 验证）。双分录 [+MAX, -MAX] sum=0 通过平衡检查 → 静默写入约 9.2 亿元×10^9 的账，审计报表无法发现。用户手工输入同样受影响。

**Required**：`resolve_source_account`（`commands/ai.rs:49`）未 trim 空 hint，`cat_lower.contains("")` 恒 true → `Some("")` 时静默返回名字最长的账户；CSV 导入（`db/import.rs:95-135`）date 无任何格式校验直接入库；`commands/data.rs:38` 把 i18n key 与 IO 错误拼成 `"errors.backupFailed: {e}"`，前端 i18n 查不到该 key。

**测试缺口**：`validate_amount` 无 inf/NaN/大数用例；`resolve_source_account` 4 个测试无空字符串用例；全仓无 i64::MAX / f64 溢出测试。

**Verdict：Request changes**（两个 Critical 阻断合并）。后端测试按用户要求仍未运行。
